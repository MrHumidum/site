# Миграции haramain.online

Перед публикацией остановите запись заказов и сделайте полную резервную копию файлов и базы. В базе есть MyISAM: одного --single-transaction недостаточно для согласованного резервного копирования; используйте блокировку таблиц или остановку записи на время копирования.

1. Выполните read-only preflight.sql и определите уже применённые миграции.
2. Для исходного дампа примените по порядку:
   - v1.1.0_lead_db_setup.sql — receipt_file, SAR, статусы 4/5, категории 100–117.
   - v1.1.1_store_identity.sql — название и оформление магазина.
   - v1.1.2_move_legacy_categories.sql — старые категории внутрь «Аптеки».
   - v1.1.3_bank_transfer_setup.sql — ручной перевод, без вымышленных реквизитов; существующие реальные реквизиты сохраняются.
   - v1.1.4_marketplace_completion.sql — страна по умолчанию, поле владельца адреса продавца, настройки регистрации/оформления.
   - v1.1.5_home_content.sql — вводный текст и отключение старой статьи о покупке лекарств в Турции.
   - v1.1.6_shipping_total.sql — включает учёт выбранной доставки в итоговой сумме, сохраняя тариф.
3. Загрузите изменённые файлы. Обновите модификации и кэш OpenCart через админку.
4. Укажите настоящие реквизиты перевода и контакты. Проверьте тариф доставки и рекламные материалы перед открытием магазина.

Не запускайте v1.1.0 повторно: она содержит безусловный ALTER TABLE. Если receipt_file, категории или SAR уже существуют, сопоставьте состояние базы со скриптами и применяйте только отсутствующие изменения. При частично выполненной миграции не запускайте всю цепочку вслепую. Скрипты рассчитаны на префикс oc_; для другого префикса требуется адаптация.

v1.1.3 и v1.1.4 написаны с защитой от повторного добавления настроек/поля; v1.1.5 обновляет конкретный существующий модуль. Повторное выполнение всей цепочки не является способом обновления.

## Откат

При ошибке оставьте магазин закрытым для записи и восстановите согласованную резервную копию файлов и всей базы. Транзакции не откатывают изменения MyISAM. v1.1.0_lead_db_rollback.sql относится только к первоначальной миграции и не является полным откатом этой доработки. После появления новых заказов/адресов нельзя без переноса данных просто удалить новые поля или восстановить старую базу: будут потеряны новые данные.

## Владение адресами

v1.1.4 добавляет oc_address.seller_id INT NOT NULL DEFAULT 0 и индекс seller_owner, если поля ещё нет. Старые записи не связываются с продавцами по совпадению числовых ID. Новые адреса продавцов используют customer_id=0, seller_id=ID продавца; адреса покупателей сохраняют прежнюю связь. Контроллеры и модели проверяют владельца.

Реквизиты задаются в админке в формате «Банк | Номер карты | Имя получателя». Пустые реквизиты блокируют подтверждение перевода. Получение чека не означает получение денег: администратор отдельно проверяет перевод.
